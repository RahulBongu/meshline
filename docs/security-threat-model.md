# Meshline Security Threat Model & Cryptographic Guarantees

This document details the security model, adversarial assumptions, and cryptographic protections implemented in **Meshline**.

---

## 1. Adversary Model & Attack Vectors

| Attack Vector | Adversary Capability | Meshline Mitigation |
|---|---|---|
| **Passive Radio Eavesdropping** | Captures all BLE advertisements and GATT packet transfers within range. | Private messages are end-to-end encrypted with **Noise XX** (`ChaCha20-Poly1305`). Group messages are encrypted with **ChaCha20-Poly1305** using epoch keys. Eavesdroppers observe only ciphertext and ephemeral packet IDs. |
| **Radio Replay Attacks** | Captures valid packets and retransmits them later to cause duplicate actions or state corruption. | **128-nonce sliding bitmask window** on Noise transport messages. Group messages bind an 18-byte Associated Data (AD) including the 2-byte big-endian epoch number; messages from past epochs fail Poly1305 MAC verification immediately. |
| **Relay Amplification / Broadcast Flooding** | Injects high volumes of packets to drain peer battery and exhaust channel capacity. | **Signature-before-deduplication**: Broadcast packets with invalid signatures are dropped before updating the deduplication cache. Per-neighbour token bucket rate limiters cap forwarding at **10 packets/second** per peer. |
| **Identity Spoofing & Sybil Attacks** | Forges a sender ID to impersonate a trusted contact or route traffic to an adversary. | **Self-certifying identities**: `senderId` is strictly the first 8 bytes of `SHA-256(Ed25519_pubkey)`. `ANNOUNCE` packets carry the public key and an Ed25519 signature over the payload. `BleTransport` binds connections only after signature verification. |
| **Key Change & Impersonation on Reconnect** | An adversary attempts to claim a known contact's nickname with a newly generated key. | **Strict Key Hold (§7.2)**: If an announce arrives with a different key for a known contact, traffic from that peer is held. `KeyChangeDialog` forces an explicit user decision. Traffic is never accepted silently. |
| **Physical Device Seizure / Forensic Extraction** | An adversary obtains physical possession of an unlocked or powered-off phone. | Database is encrypted with **SQLCipher v4 (AES-256)**. The database passphrase and Ed25519/X25519 private keys are wrapped inside the **Android Keystore** hardware module. |
| **Emergency Erase (Panic Wipe)** | User is in an immediate physical threat or coercion scenario. | **3-Tap Armed Panic Wipe**: Destroys Keystore aliases, zeros database keys, deletes SQLCipher files, purges SharedPreferences, and wipes runtime memory. |
| **Malicious Nostr Relay** | A public Nostr relay modifies, delays, or eavesdrops on internet fallback traffic. | Nostr transport is restricted to public channel broadcast fallback only. Private messages and group epoch keys **NEVER** touch Nostr relays. Core BLE mesh remains 100% offline. |

## 2. Cryptographic Specifications

### 2.1 Private Messaging (Noise XX Pattern)
Private 1-on-1 conversations implement the Signal-standard **`Noise_XX_25519_ChaChaPoly_SHA256`** handshake:
1. `-> e` (Initiator sends ephemeral public key)
2. `<- e, ee, s, es` (Responder sends ephemeral key, performs DH, sends static public key, performs DH)
3. `-> s, se` (Initiator sends static public key, performs DH)
4. Transport state established with two independent unidirectional `ChaCha20-Poly1305` cipher states.

#### Replay Protection Window
To prevent replay attacks while accommodating minor out-of-order delivery over multi-hop mesh links:
- Transport messages carry a 64-bit monotonically increasing nonce.
- A 128-nonce sliding bitmask window tracks received packet nonces.
- Packets with nonces older than the window or already marked in the bitmask are rejected before decryption.

### 2.2 Group Messaging & Epoch Security (Phase E)
Groups use symmetric AEAD encryption with epoch-based forward secrecy:
- **Epoch Key**: 32 cryptographically secure random bytes generated by the group administrator.
- **Group Tag**: 8 bytes derived via HKDF-SHA256:
  $$\text{tag} = \text{HKDF-SHA256}(\text{epochKey}, \text{info} = \text{"meshline-group-tag"}, \text{length} = 8)$$
- **Associated Data (AD)**: Exactly 18 bytes:
  $$\text{AD} = \text{groupTag (8 bytes)} \parallel \text{epoch (2 bytes BE)} \parallel \text{senderId (8 bytes)}$$
- **Sender Verification**: The receiving client checks that `senderId` belongs to an active member in the group's roster before attempting decryption.
- **Epoch Rotation**: When a member is removed or leaves, the administrator rotates the epoch key ($E \to E + 1$) and securely distributes the new epoch key to remaining members over individual Noise XX private messages.

### 2.3 Two-Tier KeyCache
To mitigate cache-exhaustion denial of service:
- **Protected Tier**: Populated exclusively by QR-code verified contacts scanned in person. Keys in this tier are never evicted.
- **Ephemeral Tier**: Populated by verified `ANNOUNCE` packets learned over the air, bounded to 256 entries using LRU eviction.

## 3. Storage Security & Emergency Wipe

- **SQLCipher v4**: Database encrypted with AES-256-CBC, 256,000 PBKDF2 iterations, HMAC-SHA512 page authentication, and 4096-byte pages.
- **Keystore Wrapping**: Passphrases and static identities are protected by hardware-backed Keystore keys (`KeyGenParameterSpec.Builder(..., PURPOSE_ENCRYPT or PURPOSE_DECRYPT)`).
- **Zeroization**: During Panic Wipe, sensitive key byte arrays in memory are overwritten with zeros, and database files are deleted from storage.
